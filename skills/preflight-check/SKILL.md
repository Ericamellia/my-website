# 发布前检查（preflight-check）

## 一句话

**它检查的是：这份代码能不能安心发出去 —— 钥匙有没有带出门（密钥）、门牌是不是写错了（公网地址）、

给别人看的说明里有没有夹带内部信息（报错泄漏）、用户会不会看到旧代码（缓存版本号）。**

## 为什么需要它

发布前的检查最容易「凭感觉」：看着仓库挺干净、页面能打开，就直接推了。
但这个项目真实踩过的坑几乎都不是「一眼能看出来」的：

| 踩过的坑 | 当时怎么发现的 |
|---|---|
| `RUN.md` 里写了 `API_KEY=eyJhbGciOi…` 占位示例，扫描器命中 | Day 23 专门写脚本才发现 |
| 改了 `app.js` 忘了升 `?v=N`，浏览器一直吃缓存 | Day 7 实测「改了没生效」 |
| 裸报错 `rest_query_failed` 直接甩给用户 | Day 23 统一错误提示时才清掉 |
| 公网接口是走 HTTP API 还是 pg 直连 | Day 19-23 反复确认（发布平台不让带 pg） |

**这些都不该靠人记得。** 该做成一个脚本，每次发布前跑一遍。

## 什么时候用它

- 准备 `git push` / 发布上线**之前**（最典型）
- 改了 `my-app/app.js` 或 `my-app/style.css` 之后（验证版本号有没有升）
- 怀疑仓库里混进了密钥 / `.env`
- 别人问「这个能发了吗」

## 怎么用

在**项目根目录**执行：

```bash
# 完整检查（含公网接口）
bash skills/preflight-check/check.sh

# 没网 / 不想打公网时：跳过 ④⑤
bash skills/preflight-check/check.sh --offline

# 改了前端 JS/CSS 时额外加的：检查版本号有没有升
bash skills/preflight-check/check.sh --staged-version
```

**退出码**：`0` = 全过；`1` = 有项没过。可以直接在 CI 里用来卡发布。

**公网地址可覆盖**（换域名时不用改脚本）：

```bash
PREFLIGHT_SITE=https://你要测的域名 bash skills/preflight-check/check.sh
```

## 检查项与判定

| # | 检查项 | 通过判定（可数） | 失败时它给你什么 |
|---|---|---|---|
| ① | 密钥泄漏 | 被跟踪文件里密钥「值」特征命中 **0 行** | 命中行数 + `文件:行号` 明细 |
| ② | `.env` 不进仓库 | 被跟踪的 `.env` 数 = **0** | 列出被跟踪的 env 文件 |
| ③ | `.env.example` 能提交 | `git check-ignore` 未命中，或命中的是 `!` 例外 | 打印命中的规则行 |
| ④ | 公网接口可达 | `/api/health`、`/api/hot`、`/api/favorites` 均 **200** | 打印实际状态码 |
| ⑤ | 错误不漏内部细节 | 错误响应体不含堆栈 / 连接串特征 | 打印泄漏出来的那一段 |
| ⑥ | 前端版本号已升 | `app.js?v=N` 的 N **大于**上一提交（仅 `--staged-version` 时查） | 打印「当前 v? → 上一提交 v?」 |

## 核心设计：为什么每一项都有「失败长什么样」

**一个永远返回「通过」的检查等于没有检查。** 所以每一项都定义了可数的失败判据，
并且**失败时必须打印证据**（哪一行、哪个状态码），而不是只报一句「失败」。

**验证这个 Skill 真的在干活的方法**（务必做一次）：

1. **正常态跑** → 应该全绿（证明不误报）；
2. **故意弄坏**：往一个被跟踪文件里加一行假密钥，例如
   `echo 'CLOUDBASE_API_KEY=eyJhbGciOiJIUzI1NiIsFakeButLooksReal000000000' >> my-app/index.html`
   （**必须是连续字符，不要带 `...` 或 `[A-Za-z` 这类符号**，否则会被当成「讨论规则的文字」排除）
   → 重跑，① 应**转红**并打印出这一行；
3. **移除后重跑** → 恢复全绿（证明检查是确定性的，不是随机）。

> 只有第 2 步通过了，才能说这个检查「不会虚报通过」。

## 三个必须知道的坑（写脚本时都踩过）

### 1. `grep -c` 无匹配时退出码是 1，别写 `|| echo 0`

```bash
# ❌ 错：grep 无匹配 → 退出码 1 → `|| echo 0` 再输出一个 0
#      结果变量变成 "0\n0"，`[ "$n" -eq 0 ]` 判断出错 → 假失败
n=$(grep -c 'xxx' file || echo 0)

# ✅ 对：统一走这个函数
count() { grep -c "$@" 2>/dev/null || true; }
```

### 2. `git check-ignore -v` 命中「`!` 例外规则」≠「被忽略」

```
.env.example → .gitignore:9:!.env.example
                           ^ 这行的规则以 ! 开头 = 未被忽略（是「例外捞回」）
```

判断要看输出行的规则是不是以 `!` 开头，不能只看有没有输出。

### 3. `curl` 不带 `-m` 超时会**永久挂住**

曾有一次脚本挂过 **26 分钟**（PATCH 请求卡住）。
**所有对外请求都要带超时**：`curl -s -m 10 ...`。

## 扫描正则为什么要排除「自证文字」

密钥扫描的正则本身会写在文档和注释里（就像你现在读的这段）。
如果只匹配「长得像 Key 的字符串」，那么**讨论这条规则的所有文字都会被命中** ——
Day 23 第一次写就被 10 条全误报淹没，真正的风险反而看不出来。

所以判据分两层：

- **只认「键值形态」**：`KEY = <20 位以上长串>`，不认散落的词（`service_role` 出现在注释里是**警告**，不是密钥）；
- **排除「自证文字」**：行里含 `...` / `…` / `[A-Za-z` / `{20,}` 等符号的，是「在讲规则」而不是「真密钥」——
  真密钥是一串连续字符，不会有这些元字符。

## 已知边界（这版没做，别以为它全能）

- **不检查代码质量 / 测试是否通过** —— 它只管「发布红线」，不管功能对不对。
- **公网检查依赖外网**：没网时用 `--offline`，此时 ④⑤ 会跳过。
- **不做自动化流水线**（这是刻意不做的）—— 它是个能手动跑出结果的脚本，不是 CI。
- **`.env` 的「值」本身不检查**：只看它有没有混进仓库，不校验格式对不对。
