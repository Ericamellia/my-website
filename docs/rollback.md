# 回滚手册（Rollback Runbook）

> 项目：东方同人查询（touhou-search）
> 线上地址：https://touhou-mock.app.workbuddy.host/
> 首次演练：Day 26（2026-10-13）
> **★ 实测数据：从「线上版本坏掉」到「线上恢复」= 59 秒；纯回退（回退命令 + 重新发布）= 53 秒。**

---

## 0. 一句话结论

**这套流程敢用。** 回退只是「把本地目录恢复到锚点 → 重新发布覆盖」，全程不到 1 分钟，且每一步都有可验证的输出（`git diff` 无差异 + 线上 `curl` 版本号正确）。唯一的前提是：**出事前必须有锚点（tag）**。

---

## 1. 什么情况必须回滚（判断表）

先判断**要不要回滚**，再动手。回滚不是第一反应 —— 先看能不能热修。

| # | 现象 | 严重度 | 处置 | 理由 |
|---|------|--------|------|------|
| 1 | 线上页面**打不开**（白屏/502/超时） | 立刻回滚 | **回滚** | 用户完全用不了，热修来不及 |
| 2 | 核心功能**报错**（列表加载失败、接口 500） | 立刻回滚 | **回滚** | 主流程断了 |
| 3 | 数据**被改错**（列表出现错内容、脏数据） | 立刻回滚 | **回滚**（必要时叠加数据恢复，见 §4） | 数据问题优先止血 |
| 4 | 页面能开但**明显错版**（错位、样式崩） | 15 分钟内热修 | 热修；修不动再回滚 | 影响观感不影响使用 |
| 5 | 文案/错别字/小样式瑕疵 | 不必回滚 | 走正常发布节奏 | 回滚反而带来新风险 |
| 6 | 只有日志报错、**用户无感** | 不必回滚 | 记录，下次一并修 | 未影响用户 |

**判断口诀**：**用户能不能正常用？** 不能 → 回滚；能但难看 → 热修；无感 → 记录。

**决策红线（不用犹豫，直接回滚）**：
- 首页 5 秒内打不开
- 任何接口返回 5xx
- 页面上出现「坏版本」「测试」「TODO」之类不该给用户看的字样

## 2. 静态托管回退（本手册的主路径）

> 适用：`deploy/` 目录下的 Node 静态服务（本项目的线上形态）。
> 本质：**WorkBuddy 的发布链接是固定的，重新发布 = 覆盖同一链接**。所以「回退」= 把本地目录恢复到旧版本 → 重新发布。

### 2.1 前置检查（10 秒）

```bash
cd <项目根>
git tag -l                    # 确认锚点存在，例如 v1.0
git log --oneline -3          # 确认当前在哪个版本
```

**没有 tag 就不能回滚** —— 这是唯一硬门槛。所以**每次发布 vX.Y 前必须打 tag**（见 §5）。

### 2.2 回退三步（实测 53 秒）

```bash
# 第 1 步：把发布目录恢复到锚点（不动其他目录）
git checkout v1.0 -- deploy/

# 第 2 步：确认恢复到位（两条命令都应为空输出）
git status --short deploy/            # 空 = 工作区与锚点一致
git diff v1.0 --stat -- deploy/       # 空 = 与锚点零差异

# 第 3 步：重新发布（覆盖同一链接）
#   用发布工具指向 deploy/ 目录即可，链接不变
```

第 3 步发布后**立刻线上验收**：

```bash
curl -s https://touhou-mock.app.workbuddy.host/api/health
#   期望看到 "version": "1.0.0"（而不是坏版本的号）

curl -s https://touhou-mock.app.workbuddy.host/ | grep -c "<坏版本特征串>"
#   期望 0
```

### 2.3 各步耗时（Day 26 实测）

| 阶段 | 动作 | 耗时 |
|------|------|------|
| ① | 制造坏版本（演练用，真实事故跳过） | 36 秒 |
| ② | 发布坏版本（真实事故跳过） | 1 分 20 秒 |
| ③ | **发现 → 执行回退命令** | **6 秒** |
| ④ | **重新发布恢复** | **53 秒** |
| ★ | **线上坏掉 → 线上恢复** | **59 秒** |

> 注意：③ 的 6 秒是「我已经知道该敲哪条命令」的情况。真实事故中，**发现问题的耗时不在此列**，取决于有没有监控。

## 3. 云函数回退（备查 · 本项目未实操）

> 本项目的线上形态是**静态托管**，不走云函数。此节仅供将来切换架构时参考。

### 3.1 与静态回退的区别

| 维度 | 静态托管 | 云函数 |
|------|----------|--------|
| 回退对象 | `deploy/` 目录 | 函数代码包 |
| 回退方式 | `git checkout` + 重新发布 | 控制台上传旧版本包 / 重新部署 |
| 是否影响数据 | 否 | **可能**（若函数里有迁移逻辑） |
| 回退速度 | 快（< 1 分钟） | 较慢（打包 + 上传 + 冷启动） |
| 可回退版本 | 任意 tag | 取决于控制台保留的历史版本 |

### 3.2 云函数回退步骤（将来参考）

1. **确认目标版本**：在云开发控制台 → 云函数 → 版本管理，找到上一个正常版本
2. **下载旧版本包**（或直接用控制台的「回退到该版本」）
3. **上传并部署**
4. **验证**：调用 `health` 类接口，确认版本号
5. **若失败**：不要反复重传 —— 停下，确认包是否完整、配置是否一致

**关键差异**：云函数回退**可能带着数据副作用**（比如函数启动时跑迁移）。所以云函数出事时，**先判断是「代码问题」还是「数据问题」** —— 代码问题回退代码，数据问题见下节。

## 4. 数据恢复（备查 · 本项目未实操）

> 本项目数据有两层：**CloudBase 真库（PostgREST）** 和 **`deploy/data/*.json` 快照降级**。

### 4.1 先分清数据在哪一层

| 现象 | 数据来源 | 恢复动作 |
|------|----------|----------|
| `health` 的 `dataSource: "rest"` | 真库 | 见 §4.2 |
| `health` 的 `dataSource: "snapshot"` | 本地 JSON 快照 | 见 §4.3 |

`curl .../api/health` 一眼能看出当前走哪条通道。

### 4.2 真库数据恢复

1. **立即停写**：先让前端/接口不再写入（回退代码到只读版本，或临时下线写接口）
2. **定位范围**：确认哪些表、哪些行被改错（用 `created_at` / `updated_at` 圈定时间窗）
3. **优先软删**：本项目表结构带 `is_deleted` 字段 —— **改错优先用软删标记，不要物理删**
4. **从快照补**：`deploy/data/*.json` 是某时刻的全量快照，可作恢复源
5. **验证**：恢复后用接口查一遍受影响的数据

**红线**：**不要在没有备份的情况下对生产库跑 `DELETE` / 无 `WHERE` 的 `UPDATE`。**

### 4.3 快照（JSON）恢复

```bash
git checkout v1.0 -- deploy/data/
```

快照文件在 git 里，**直接 checkout 就是恢复** —— 这是本项目数据层最省事的恢复方式。

## 5. 发布规范（防患于未然）

回滚能快，靠的是**发布时就留好锚点**。

### 5.1 每次发布前的检查清单

1. 跑 `preflight-check`（`skills/preflight-check/check.sh`），7 项全过
2. **打附注 tag** 并推送：
   ```bash
   git tag -a v1.1 -m "v1.1：<一句话说明>"
   git push origin v1.1        # 注意：tag 要单独推，git push 默认不带 tag
   ```
3. 发布
4. **线上验收**（`curl /api/health` 看版本号 + 首页 200）

### 5.2 tag 命名约定

- `vX.Y`：对外发布版本（如 `v1.0`）
- `vX.Y-<说明>`：实验性快照（如 `v1.0.1-rollback-drill`）
- **回滚锚点只认正式 tag**，不认实验性 tag

## 7. 敢不敢用？—— 诚实的回答

**敢，但有三个前提**：

1. **必须有 tag 锚点** —— 没有锚点，这套流程一步都走不了。解决：把「打 tag」写进发布清单（§5.1）。
2. **必须能重新发布** —— 发布工具不可用时，回退卡在第 3 步。这是**单点依赖**，目前无备选方案。
3. **发现要够快** —— 53 秒是「知道要回退之后」的耗时。真实事故中**发现问题的耗时可能远大于回退本身**。当前没有自动监控，靠人工发现。

**已知短板（诚实记录）**：
- 无自动健康检查/告警 → 发现问题靠人
- 发布工具是唯一通道 → 无备用发布路径
- 数据层恢复（§4）**未实操过**，只写了步骤

**下一步该补的**：给线上加一个定时健康检查（可用自动化任务），出问题主动通知 —— 这比优化 53 秒更有价值。
