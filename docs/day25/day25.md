> 我往**一个被 git 跟踪的文件**（`my-app/index.html`）里注入了一行**形如真 Key 的连续长串**

每一项都对应**这个项目真实踩过的坑**：

| 来源 | 踩过什么 | 变成哪一项 |

### 1.2 六项检查与判定

| # | 检查项 | 通过判定（可数） |
|---|---|---|
| ① | 密钥泄漏 | 被跟踪文件里密钥「值」特征命中 **0 行** |
| ② | `.env` 不进仓库 | 被跟踪的 `.env` 数 = **0** |
| ③ | `.env.example` 能提交 | 未被忽略（或命中 `!` 例外） |
| ④ | 公网接口可达 | `/api/health`、`/api/hot`、`/api/favorites` 均 **200** |
| ⑤ | 错误不漏内部细节 | 错误响应体不含堆栈 / 连接串特征 |
| ⑥ | 前端版本号已升 | `app.js?v=N` 的 N **大于**上一提交（可选，`--staged-version`） |

### 1.3 设计原则（今天真正学到的东西）

**每一项都必须定义「失败长什么样」。**

这是规划阶段最重要的一条。如果只写「检查有没有密钥」，那这个检查**永远可以报通过** ——
因为没有定义什么情况算失败。所以每一项都写成**可数的判据**（命中 0 行 / 数等于 0 / 状态码等于 200），
并且**失败时必须打印证据**（哪一行、哪个状态码），否则用户看到「失败了」也不知道改哪。

## 2. 板块②：制作检查 Skill

### 2.1 交付物

```
skills/preflight-check/
├── SKILL.md      # Skill 说明（触发场景 / 检查项 / 判定 / 三个坑 / 已知边界）
├── check.sh      # 检查脚本（零依赖：git + curl + grep）
└── RUN_LOG.md    # 调用记录
```

`SKILL.md` 带前置元数据（`name` / `description` + 触发场景），能被 Skill 工具识别：

```yaml
---
name: preflight-check
description: 发布前检查 —— ...触发场景：准备 git push / 发布上线前；改了 app.js 或
  style.css 之后；怀疑仓库里混进了密钥；用户问「可以发了吗 / 上线前要不要检查什么」。
agent_created: true
---
```

### 2.2 脚本设计上的三个决定

1. **退出码 = 0/1**：全过 0、有失败 1。这样以后就算真上 CI，也能直接用来卡发布。
2. **失败必须带证据**：① 打印命中的行；④ 打印实际状态码；③ 打印命中的规则行。
3. **公网地址可被环境变量覆盖**（`PREFLIGHT_SITE=`）：换域名不用改脚本。

### 2.3 写脚本时踩的三个坑（都写进了 SKILL.md）

**坑 1：`grep -c` 无匹配时退出码是 1，别写 `|| echo 0`**

```bash
# ❌ 错：grep 无匹配 → 退出码 1 → `|| echo 0` 再输出一个 0
#       变量变成 "0\n0"，[ "$n" -eq 0 ] 判错 → 假失败
n=$(grep -c 'xxx' file || echo 0)

# ✅ 对：统一走这个函数
count() { grep -c "$@" 2>/dev/null || true; }
```

（这个坑 Day 23 踩过，导致脚本挂了几十分钟。）

**坑 2：`git check-ignore -v` 命中 `!` 例外规则 ≠ 被忽略**

```
.env.example → .gitignore:9:!.env.example
                           ^ 规则以 ! 开头 = **未被忽略**（是「例外捞回」）
```

判断要看输出行的规则是不是以 `!` 开头，不能只看有没有输出。

**坑 3：`curl` 不带 `-m` 超时会永久挂住**

曾挂过 **26 分钟**。所有对外请求都带超时：`curl -s -m 10 ...`。

### 2.4 扫描正则的修正（第一版就误报了）

第一版直接扫「所有被跟踪文件」，结果**命中 7 行** —— 全是 `docs/day23/` 里
**讨论这个正则本身**的文字（`eyJhbG…` 省略号占位、正则源码 `[A-Za-z0-9_-]{20,}`）。

这正是 Day 23 踩过的同一个坑的变体：**扫描器会命中"在讲密钥格式的文字"**。

修法：加一条**排除「自证文字」**的规则 ——
行里含 `...` / `…` / `[A-Za-z` / `{20,}` 等**元字符**的，判为「在讲规则」而不是真密钥。
（真密钥是一串连续字符，不会有这些符号。）

```
修前：命中 7 行（全是自证文字，误报）
修后：命中 0 行（干净）
```

> 这一条还有个**副作用要注意**：故意注入的假密钥**必须是连续字符**，
> 否则会被当成「自证文字」排除掉，验证实验就假了。这一点写进了 SKILL.md。

## 3. 板块③：实跑验证（今天的重点）

### 3.1 三步验证法

**先想清楚：怎么证明一个检查「不会虚报通过」？**
答案是：**故意弄坏给它看**。分三步，缺一不可：

| 步骤 | 操作 | 期望 | 实际 |
|---|---|---|---|
| 1 | 正常态直接跑 | 全绿（不误报） | **通过 7 项，失败 0 项** ✅ |
| 2 | 注入一行假密钥 | ① 转红 + 打印该行 | **① 转 [FAIL]，命中 1 行** ✅ |
| 3 | 移除后重跑 | 恢复全绿（确定性） | **通过 7 项，失败 0 项** ✅ |

### 3.2 故意留的问题怎么选

选**检查项 ①（密钥泄漏）**，理由：

- **能确定性制造**：注入一行 `CLOUDBASE_API_KEY=<连续长串>` 即可；
- **改一行就能恢复**：注入 / 还原都很干净，不留后患；
- **Day 23 已验证过这条正则能命中 JWT 特征串** —— 即**这条检查真的会失败**。

注入位置选 `my-app/index.html`（**被 git 跟踪**的文件 —— 检查只扫被跟踪文件，
扫工作区里没跟踪的文件是查不出来的）。

### 3.3 第 2 步的实测输出（原文摘录）

> 为了让本文档自身不被扫描器命中（Day 26 才发现这个副作用），下面把注入值中部略去，
> 以 `<假密钥>` 代替；原始完整输出见 `evidence/step2-injected.txt`。

```
---- ① 密钥泄漏：被跟踪文件里有没有密钥「值」特征 ----
  [FAIL] ① 密钥泄漏  命中 1 行 —— 明细如下：
         my-app/index.html:<meta name="x-preflight-probe" content="CLOUDBASE_API_KEY=<假密钥>">

...（其余项仍 PASS）...

汇总：通过 6 项，失败 1 项
>>> ❌ 有 1 项没过，先修再发：
      - ① 密钥泄漏
```

**关键点**：它不只报「失败」，还**指出了是哪一行**（`my-app/index.html:...`）。
没有这一句，用户拿到「失败」也不知道去哪改。

### 3.5 这一步真正的价值

用户今天要掌握的那句话，落到实处就是：

> **一个永远报「通过」的检查，等于没有检查。**

如果我只写脚本、跑一次看到全绿就收工，那我**无法区分**这两种情况：
- 「项目真的没问题」
- 「脚本写错了，它不管什么时候都报通过」

只有**故意弄坏、看它是否变红**，才能排除掉第二种可能。

## 5. 本次踩到的一个新坑：Python 写文件会改换行符

验证脚本第一版用**文本模式**读写注入文件：

```python
with open(f, 'r', encoding='utf-8') as x: original = x.read()   # 读
with open(f, 'w', encoding='utf-8') as x: x.write(injected)     # 写
```

结果：Windows 下 LF 被转成 CRLF，文件从 **9010 字节涨到 9145 字节**，
`git status` 出现「不明修改」（而 `git diff` 却是空的 —— CRLF 的典型表现）。

**修法**：改用**二进制模式** `open(..., 'rb')` / `open(..., 'wb')`，
连换行符一起精确还原。改完重跑，工作区完全干净。

> 教训：**凡是「改了要还原」的操作，都要二进制读写** —— 文本模式会偷偷动换行符。
