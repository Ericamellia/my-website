# Day 25 · 板块① 规划：发布前检查 Skill 要检查什么

> 目标：产出一个**可复用**的「发布前检查」Skill —— 每次要发布/推送前跑一遍，
> 把「上线红线」和「最容易翻车的地方」过一遍，并给出**能亲眼确认**的结论。
>
> 设计原则（今天要掌握的）：**每一项都必须有「失败长什么样」的定义** ——
> 否则 skill 只能永远报「通过」，那它就是个摆设。

## 2. 检查项清单（v1，共 6 项）

| # | 检查项 | 为什么是红线 | 通过判定 | 失败长什么样 |
|---|---|---|---|---|
| 1 | **密钥泄漏** | 泄漏 = 任何人可绕过权限读写生产库 | 被跟踪文件里密钥「值」特征命中 **0 行** | 命中 ≥1 行，打印出文件:行号 |
| 2 | **`.env` 不进仓库** | 同上，凭证泄漏 | `.env` 被跟踪数 = 0，且 `.env` / `.env.local` 被 ignore | 有输出 → 列出被跟踪的 env 文件 |
| 3 | **`.env.example` 能提交** | 它是给协作者的模板，被误忽略就没用了 | `git check-ignore` 未命中，或命中的是 `!` 例外 | 被忽略 → 报「模板提交不了」 |
| 4 | **公网接口可达** | 发布后用户第一眼就是打不开 | `GET /api/health` 等信息接口 **200** | 非 200 / 超时 → 打印实际状态码 |
| 5 | **公网接口不返回内部细节** | 报错里漏堆栈/连接串 = 二次泄漏 | 错误响应体里**不含** `ECONNREFUSED` / `at Object.` / 连接串 | 命中关键字 → 打印响应体 |
| 6 | **前端版本号已升** | 改了 JS/CSS 不升版本 = 用户看到旧代码 | `app.js?v=N` 的 N **大于**上一提交的 N | 相等或变小 → 报「缓存没绕过」 |

**今天刻意不做**（用户明确排除）：把检查做成自动化流水线（CI / pre-commit hook）。
只做「能手动跑出结果」的 Skill。

## 3. 故意留的问题（用来验证 Skill 不虚报）

用户要求：「故意留个问题它能查出来」。

**选它作为「故意留的问题」→ 检查项 1（密钥泄漏）**，理由：
- 能**确定性地制造**：往一个被跟踪文件里写一行形如 `CLOUDBASE_API_KEY=eyJhbGciOiJIUzI1NiIsVeryLongFakeValue1234567890` 的内容；
- **制造和恢复都很干净**：改一行、跑一次、删掉即可，不留后患；
- Day 23 的扫描脚本已验证过它能命中 JWT 特征串 —— 即**这条检查真的会失败**。

验证方式（三步，缺一不可）：
1. **正常态跑** → 全绿（证明没误报）；
2. **注入假密钥** → 检查项 1 **转红**，打印出注入的那一行（证明没虚报通过）；
3. **移除后重跑** → 恢复全绿（证明检查是确定性的，不是随机）。

> 这一步才是今天的重点：**一个「永远通过」的检查等于没有检查**。
> 故意弄坏、看它是否变红，是唯一能证明它真在干活的方法。

---

## 4. 判定上的两个讲究

1. **「通过」要有明确阈值，不能是「看起来没问题」** —— 每项都是「命中数 = 0」这种可数、可复现的判据。
2. **失败必须带证据** —— 不能只说「失败」，要打印出「哪一行 / 哪个状态码 / 哪个文件」，否则用户没法修。
